# 1. Purpose
Проект состоит из двух приложений для Raspberry Pi:
Collector — раз в сутки по расписанию получает измерения температуры и влажности с беспроводных датчиков и сохраняет их в SQLite.
Dashboard — предоставляет web-страницу с графиками (в браузере) в локальной сети, читая данные из SQLite.
Цель: автономный локальный мониторинг за последние N дней/месяцев без облака.

# 2. Non-goals
Облачный доступ, авторизация пользователей, публичный доступ из интернета.
Управление датчиками (прошивки, настройки радиоканала и т.п.).
Высоконагруженный продакшен: проект для личного использования.
Видеостриминг, уведомления (можно добавить позже отдельным модулем).

# 3. Runtime environment
Target: Raspberry Pi (Linux).
Python 3.12+ (предпочтительно), запуск в venv.
Storage: локальный файл SQLite (.db) на диске.
Сеть: доступ по LAN, без обязательного TLS.

# 4. High-level architecture
## collector (CLI/скрипт):
запускается cron/systemd timer раз в сутки
читает список датчиков из конфигурации
получает измерения (температура/влажность) через драйвер/адаптер
пишет в SQLite (идемпотентно, без дублей)
логирует результат (сколько датчиков, сколько записей, ошибки)

## dashboard (веб-сервис):
запускается как сервис (systemd)
читает SQLite только на чтение
отдаёт HTML-страницу с графиками
предоставляет фильтры: период времени и выбор датчика(ов)

# 6. Configuration
Единый конфиг-файл (например config.toml):
- database_path: путь к .db
- collector:
  - enabled_sensors: список sensor_id или правило автообнаружения (первый этап — список)
  - driver: имя драйвера (например ble, rtl_433, vendor_x) — на первом этапе допускается “заглушка”
  - max_age_days: сколько дней держать данные (опционально, для ретенции)
- dashboard:
  - host (по умолчанию 0.0.0.0)
  - port (например 8080)
  - default_range_days (например 30)
  - refresh_seconds (например 300)

# 7. Collector specification
## 7.1 Behavior
S1. Daily run stores readings
Given: в конфиге 2 включённых датчика, драйвер возвращает по одному измерению на датчик
When: collector запускается
Then: в readings появляются массив записей за прошедшие сутки с корректным sensor_id и ts_utc

S2. Idempotent insertion
Given: в базе уже есть запись (sensor_id, ts_utc)
When: collector повторно получает то же измерение
Then: в базе не появляется дубль (insert игнорируется или заменяется без увеличения количества строк)

S3. Partial failure does not break full run
Given: один датчик отвечает, второй даёт ошибку чтения
When: collector запускается
Then: записи сохраняются для успешного датчика, ошибка логируется, общий процесс завершается с кодом:
0, если хотя бы часть датчиков успешна (можно выбрать строгий режим позже)
!=0, если все датчики неуспешны

S4. Validation
Given: драйвер вернул temperature_c вне диапазона (например < -50 или > 100)
When: collector пытается сохранить
Then: запись отклоняется, логируется как некорректная, процесс продолжает работу

S5. Retention (optional)
Given: включён max_age_days=90
When: collector завершает успешный проход
Then: записи старше 90 дней удаляются

## 7.2 CLI
collector run --config /path/config.toml
Exit codes:
0: успех (все или частично успешные датчики)
2: ошибка конфигурации/БД
3: все датчики недоступны/ошибка драйвера

## 7.3 Logging
stdout/stderr или файл (решение реализационное), но лог обязательно содержит:
- start/end timestamp
- количество датчиков
- количество сохранённых записей
- список ошибок по датчикам (без падения процесса)

# 8. Dashboard specification
## 8.1 Web UI (single page)

D1. Main page available
Given: сервис запущен
When: открыть http://<pi-ip>:<port>/
Then: отдается HTML-страница с:
- выбором датчика (dropdown/multi-select)
- выбором диапазона (последние 24 часа / 7 дней / 30 дней / кастом)
- графиком температуры и влажности по времени

D2. Empty state
Given: в базе нет данных для выбранного датчика/периода
When: открыть страницу
Then: показывается “Нет данных за выбранный период”, без ошибок 500

D3. Multiple sensors
Given: выбраны несколько датчиков
Then: графики отображают либо:
- отдельные серии по датчикам, либо
- отдельные панели на датчик
(на первом этапе — отдельные серии на одном графике)

D4. Refresh
Given: refresh_seconds задан
Then: страница автообновляет данные без полной перезагрузки (допускается простое обновление страницы на первом этапе)

## 8.2 HTTP endpoints
GET / — HTML
GET /api/readings?sensor_id=...&from=...&to=...
возвращает JSON, отсортированный по времени
параметры from/to принимают ISO-8601, по умолчанию to=now, from=now-default_range_days

GET /health — 200 OK если сервис жив и может открыть базу

## 8.3 Performance constraints
Типичный запрос за 30 дней по одному датчику должен отрабатываться за приемлемое время на Pi (цель: < 1–2 сек).
Выборка должна быть ограничена по числу точек (опционально): downsampling/агрегация по часу/10 минут.

# 9. Security / access
По умолчанию доступ только в локальной сети.
Не хранить секреты в репозитории.
Если будет добавлена авторизация — отдельная спецификация.

# 10. Testing strategy (SDD)
Unit tests: валидация данных, идемпотентные вставки, ретенция.
Integration tests: SQLite schema migration + вставка/выборка.
API tests: /api/readings, /health (через test client).
